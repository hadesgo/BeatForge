**原始需求复述**：用户把自己的照片和视频连同歌曲交给 BeatForge，自动生成的 MV「很有廉价感，像粗制滥造，一点都不精良」。这不是功能缺失——功能全都在，特效甚至过多——而是**整片层面的编排失控**：剪辑节奏、素材复用、画面处理、字幕、调色五条线各自局部正确，合起来互相拆台。

## 1. 产品目标

改造后，同一批素材、同一首歌，应当产出一支**有呼吸、有记忆点、画面干净**的 MV：
快慢有对比、副歌能紧、前奏尾声能松；少数画面反复回来形成母题而不是 255 张互不相识的照片；每一帧只有一个主体、一个画框、一套可读的字；全片像被一个人调过色，而不是被三个滤镜各叠了一遍。**衡量标准不是"更好看"，而是第一节列出的六个维度全部落入阈值区间，并且可以自动回归。**

---

## 2. 用户故事

1. 作为**把手机相册里的照片和一段歌丢进来的普通用户**，我希望成片不要像把 300 张照片按顺序播一遍，而是有些画面会回来，让我觉得"这是一支片子"。
2. 作为**在 `project.toml` 里写下了 `subtitle_layout = "band"` 的用户**，我希望成片真的用底部字幕条，而不是程序悄悄换成自由版式还不告诉我。
3. 作为**只提供竖版手机照片的用户**，我希望竖图出现在横屏里时不要出现"同一张脸被放大糊掉衬在背后"这种一眼假的画面。
4. 作为**在亮沙滩、雪地、白云这类明亮照片上打字的用户**，我希望字幕在任何一帧都读得出来，而不是只有背景暗的那几句能看清。
5. 作为**把微信二压过的 JPEG 交给程序、又不想画面变"脆、脏、假"的用户**，我希望程序不要在我的压缩图上再叠两层饱和度和对比度，还附赠无条件颗粒与暗角。

## 3. 「精良」的可操作定义（全文最重要的一节）

把「精良」拆成 **6 个维度**。每个维度有一条**测量程序**（跑什么、读什么产物）、一个**阈值**、一个**可自动断言**的结论。所有测量都落在既有产物上：`plan.json`、`lyrics.ass`、渲染出的 `clips/*.mp4`、滤镜图字符串、成片抽帧的像素统计。**不接受任何无法自动判定的表述。**

| # | 维度 | 测什么（产物 → 统计量） | 现状实测 | 目标 |
| --- | --- | --- | --- | --- |
| D1 | **节奏对比度** | `plan.json` shots[].duration 的分布；逐段平均镜长与导演 `cut_intensity` 的相关性 | 平均 0.775s，**81% < 0.8s**，最长仅 1.90s（几乎无长镜） | 短镜占比 ≤ 55%；p90/p10 ≥ 2.0；intro/outro 均长 ≥ 1.5× 全片均长；与 `cut_intensity` 的 Pearson r ≤ −0.6 |
| D2 | **复现度（记忆点）** | `plan.json` 的 media_id 复用分布、`motif_appearances` | **零复用**（255 镜头 / 255 个不同素材）；5 个导演母题出现 1/0/1/1/1 | 每个母题 ≥ 3 次；全片复现镜头占比 8%–30%；≥ 60% 的复现集中在母题上 |
| D3 | **画面单一性** | 单图镜头滤镜图谓词 + 渲染帧的接缝阶跃与同图 NCC | 182/182 单图镜头都是「虚化双胞胎 + 92% 硬边内嵌」 | 滤镜图不含同源虚化底叠内嵌；接缝无孤立阶跃；同图双尺度 NCC ≤ 0.6；一帧内加框元素 ≤ 1 |
| D4 | **字幕可读性** | `lyrics.ass` 的 `\pos`/配色/时长 + 带字幕帧与无字幕参考帧的字形掩码差 | `\pos` 98 处（配置要 band）；配色白/金混用；46px 发丝描边落在亮沙上不可读 | band 模式下 `\pos` = 0；字形掩码平均 \|Δluma\| P10 ≥ 24/255 且 min ≥ 12/255；全片主色取值集合 = 1；每个事件 ≥ 0.6s |
| D5 | **影调克制** | 单镜滤镜图里串联的调色算子数与总增益；暗角/颗粒的命中条件 | 每镜串联 3 层色彩算子（shot_match + grade + section_color）+ 无条件 `noise=1.6` + 无条件 `vignette` | 每镜改变 luma/saturation 的算子 ≤ 2；总 saturation 增益 ≤ 1.10；压暗镜头不加暗角；已含噪源不加颗粒 |
| D6 | **交付规范** | `ffprobe` 成片 stream 元数据 | `pix_fmt = yuvj420p`（**全范围**）、17.8 Mbps / 446 MB | `color_range = tv`、`pix_fmt` 不以 `yuvj` 开头；颗粒成本下降而非靠抬 CRF |

**三个维度的共同点（也是本节的结论）**：D1 决定「看不看得见」，D2 决定「记不记得住」，D3/D4/D5 决定「每一帧干不干净」。现在的成片在**三个维度上同时**落在阈值的错误一侧——**21 种运镜、31 种版式摊在 0.775 秒上，观众一个都看不到；零复现让母题在数学上不可能生效；三层调色叠在已经压过的 JPEG 上把画面推成"脆、脏、假"**。所以本需求池的第一条不是"加效果"，而是"让已有的效果和意图能落到画面里"。

### 4.1 分级说明（为什么这样分，以及我偏离了诊断的分级）

分级标准 = **对「廉价感」的贡献度 × 改动风险**（贡献大且风险可控 → P0）。

- **诊断的五条 P0 我全部保留为 P0**，但做了一处**重排**：诊断把 P0-A（节奏）与 P0-D（字幕静默覆盖）并列，我认为二者共享同一个成因（**程序的决定静默压过用户的配置**），所以抽出 **R-02 作为一条跨条目的通则性 P0**，让 P0-A / P0-D 的具体症状成为它的两个实例 + 另外三条独立 P0（R-01 节奏、R-03 母题、R-04 画面、R-06 影调）。
- **我把「转场词汇过载」定在 P1 而不是 P0**，理由是：它有一半是 P0-A 的**下游症状**——一旦 R-01 让转场按逐段 `transition_tone` 授权，58 个冲击型里大部分会自动消失。剩下的「22 种太多」是纯粹的词汇表收敛，改动小、风险低，但不解决它并不会让人继续觉得「廉价」到不可交付。**我把它从诊断的「次要」提到 P1**，因为 58 个冲击型砸在「温情纪实」上，是抽帧之外最直接的一条廉价感来源。
- **「视频素材被饿死」我定 P1**（与诊断一致），因为 9% 确实偏低，但它不是一个"错误"，只是一个配比；**「素材质量无兜底」我也定 P1**，因为它会直接产出 `out_05_130s.png` 这种一眼假镜头，但修复需要在打分里加硬闸门、动到选镜逻辑，风险中等。
- **`camera_motion` 我定 P2 并给了"补全或移除"的二选一**，而不是笼统地"确认是否移除"：它虽然被打分和导演提示词引用（所以不是纯装饰），但影响面窄、不改变成片观感，属于交付卫生问题。**注意它与 R-02 同源**：一个字段 255/255 全是默认值，本身就是「静默失效」的一种，所以它必须留下显式记录（要么补全、要么删掉），不允许继续以"unknown"静默存在。

## 5. 约束

1. **不得破坏 README 记录、且有测试钉住的既有不变式。** 诊断第 4 节列出的七条全部继续成立，任何需求都必须在其内实现，尤其：
   - 多图合成不得把两张素材画在同一片像素上；
   - 分割版式各格宽度之和必须等于画布宽度；
   - `_quad_spread` 与 `_camera_quad` 用同一个 `amount`，测试/探针扫过整个区间；
   - 门控/版式轮转按镜头序号、运镜轮转按已选单图镜头数，三个计数器不可合并；
   - `fontsdir` 只能一个目录，ASS 里的家族名必须是实际存在的那个拼写；
   - 滤镜图能被 ffmpeg 接受，长片用 `-/filter_complex` 从文件读；
   - `uv run pytest -q` 与 `ruff` 全绿。
   **特别提示**：R-04 会动到单图处理，而 README §412 用大段篇幅论证「虚化底在合成里是错的、单图才保留留边处理」——R-04 事实上要推翻这条单图例外。**这是对既有设计的有意修正，必须在 README 里改写对应段落并说明理由，不能只改代码。**

2. **不得静默破坏向后兼容。** 现有 `demo/project.toml` 与 `my-mv/project.toml` 都是有效工程。凡需要改变默认行为的需求，必须明确「旧工程重新渲染会得到什么不同结果」：
   - **R-03 改变了 README §489 明文承诺的「素材够用时全片零复用」**。旧工程重渲后，母题素材会复现（≥3 次）、非母题仍不复用。这是**有意的行为变更**，必须写进 README 与 release note；`scripts/reuse_probe.py` 的期望输出要同步改。
   - **R-01 改变了「`edit_style != manual` 时接管镜长」的实际效果**。旧工程 `my-mv`（用户写 `min_shot_seconds=1.8/max_shot_seconds=5.5`，`edit_style=auto`）重渲后节奏会变慢、冲击段变紧。必须在 README「关键配置速查」里补齐被接管的第四项（`subtitle_layout`）并说明冲突解决优先级。
   - **R-06 改变了交付像素格式**（`yuvj420p` → limited range）。旧工程重渲后成片整体亮度/对比会有轻微但可见的变化，第三方向导重编码不会再有 range 歧义。
   - **R-04/R-05 改变单图镜头与字幕的视觉呈现**，旧工程重渲后画面构成与字幕外观都会变；这类属于"目标本身"，但也需在 README 说明。

3. **必须消除「静默配置失效」这一类缺陷（R-02 为通则）。** 用户写在 `project.toml` 里的配置被程序悄悄无视，是本项目历史上反复栽的坑（字体目录不可达、分离模型降级、家族名拼错、以及本轮 P0-A 与 P0-D）。**通则：任何「程序的决定覆盖用户的配置」都必须要么在 README 明示，要么在日志显式告知——不允许静默。** 具体形式：
   - 日志一行 WARNING，形如 `<配置项>: requested=<用户值> effective=<实际值> overridden_by=<edit_style:beat | subtitle_layout:free | ...>`；
   - `plan.json` 落一个 `config_audit` 段，机器可读、可回归；
   - README 的接管清单必须与实际接管清单一致（含本轮补上的 `subtitle_layout`）。
   这条通则**优先于**其他需求的具体取舍：任何"让程序更聪明地替用户做决定"的设计，都不得以静默为前提。

4. **全量测试与静态检查必须保持全绿。** `uv run pytest -q`（约 370 条，不下载模型）与 `ruff` 必须干净。新增判据应以测试或探针的形式落下来，且**不得要求下载模型或在 GPU 上运行**。

## 6. 待确认问题

以下四条确实是歧义，需要用户拍板后才能定死阈值：

1. **「温情纪实」下，用户配置与导演意图谁优先？** 导演 concept 写「温情纪实短片」，用户却在 `project.toml` 显式写了 `min_shot_seconds=1.8 / max_shot_seconds=5.5`（介于 `lyric` 1.6–4.6 与 `cinematic` 3.0–6.5 之间），而 `edit_style=auto` 按情绪选中了 `beat`（0.55–1.9）。R-02 能保证"不再静默"，但**默认该听谁的**需要用户决定：(a) 用户显式值优先，风格只在用户未表态时接管；(b) 风格优先，但必须显式告知；(c) 二者取交集/折中。
2. **末段制是否接受「把单图也改成全出血裁切」？** R-04 的最彻底解法是让单图与视频一样做主体感知的全出血裁切，但那样 `image_foreground_scale` 与 `blurred_image_background` 两个既有配置项就失去意义（README §375 明文宣传过）。需要用户确认：**是保留留边但换掉虚化底（例如用主色渐变/纯色底），还是彻底废弃这两个配置项？**
3. **母题复现的最低次数 3 次是否合适？** 阈值应否与歌曲段落数挂钩（例如"每个出现的段落至少一次"），还是固定常数？这决定 R-03 的判据是硬常数还是自适应。
4. **字幕的默认视觉兜底到哪里为止？** 现状 `subtitle_size=46 / subtitle_outline=1.1`，README 说参考片是**完全无描边**。要让字在亮沙滩上也读得出来，可选手段有：加粗描边、加半透明底衬（scrim）、局部压暗、或 `knockout` 镂空。**用户是否接受"默认给字幕加一层轻底衬"**（会略微改变"融入画面"的风格），还是坚持"只靠描边/局部压暗"？
5. **`camera_motion` 的期望状态**：用户是否真的会在素材 sidecar 里维护这个字段？如果不会，R-11 应直接选择"移除"，而不是要求补全。
