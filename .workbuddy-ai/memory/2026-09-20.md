## 真机报「director_llama_server 指向的文件不存在：.」——两个真 bug + 导演首次真机跑通
用户反馈：5070 真机上「本地导演不可用，使用规则导演：LlamaServerError:
director_llama_server 指向的文件不存在：.」。**注意路径部分是空的**，这是关键线索。
顺带纠正了上一条"开发机无独显"的结论——真机就是这张 5070 12GB。

### Bug 1：`Path | None` 把空字符串折叠成 `Path(".")`
`director_llama_server = ""`（模板里就是这么写的，"留空即自动查找"）经 pydantic 变成
`Path(".")`——**不是 None**，于是 `find_server_binary` 走"显式路径"分支，在**PATH 与
`<cache>/bin` 查找之前**就抛错，`str(Path("."))` 就是那个孤零零的 `.`。
同一个坑还有三处：`director_gguf`、`render.subtitle_fonts_dir`（Path(".") 是 truthy 且 exists，
会把项目根目录当成字体目录扫）、`project.lyrics`（`lyrics = ""` 是文档里的写法，折叠后
pipeline 里"已经有歌词了吗"答"有"，接着把一个目录当 LRC 读）。
修法：`config._blank_path_is_none()` + 四处 `field_validator(mode="before")`（空串和 `.` 都按未配置）。
守门测试里有一条**端到端回归**：用真模板 + 只在 `<cache>/bin` 放 `llama-server.exe`，
断言 `find_server_binary` / `find_gguf` 都能找到。

### Bug 2：CUDA 构建缺运行时 DLL，进程在加载期就死且零输出
解决 Bug 1 后，`llama-server.exe --version` 仍返回 `0xC0000135 (STATUS_DLL_NOT_FOUND)`，
**没有任何 stdout/stderr**。定位过程（值得复用）：
1. 写了个**纯 Python PE 导入表解析器**（无第三方依赖）——但 `api-ms-win-crt-*` 那些是 API set
   契约、磁盘上没有对应文件，会误报"缺失"，得排除；
2. 更有效的是**按依赖顺序用 `ctypes.WinDLL` 逐个加载**：`ggml-base`/`ggml-cpu` 成功，
   `ggml-cuda.dll` 失败；
3. `ggml-cuda.dll` **静态导入 `cublas64_13.dll`**，而机器上完全没有 CUDA toolkit；
4. 但 `.venv\Lib\site-packages\torch\lib` 里有 `cublas64_13.dll` / `cublasLt64_13.dll` /
   `cudart64_13.dll`（torch 2.14+cu130 自带）；
5. 把这目录加到子进程 PATH → `--version` 立刻输出 `version: 0.2.0-dev (build 10709)`。
修法：`llama_server._launch_environment()` 把 **bin 目录放最前**、torch 的 CUDA 运行时其后，
交给 `Popen(env=...)`；并把 `0xC0000135/0xC0000139` 解码成人类可读的提示
（"缺运行时 DLL，不是模型问题"），否则用户只会看到"启动后立即退出"而毫无线索。

### Bug 3（最隐蔽）：R1 风格推理模型会烧光预算，`content` 返回空
第一次冒烟测试"通过"了但回复是**空字符串**——差点当成成功。查原始响应才发现：
- 短问答 `finish_reason=stop`，正确内容在 `content`，而 632 字的思考过程在 `reasoning_content`；
- 给 16/128 tokens 时，**全部被思考吃掉**，`content=''`、`finish_reason=length`。
模型自带 Jinja 模板支持 `enable_thinking`；三种方案实测：
- 默认（开思考）：170 tokens 拿到结果；
- `chat_template_kwargs={"enable_thinking": false}`：**14 tokens、零思考、直接给 JSON**；✅
- `reasoning_budget: 0`：**这个构建（b10709）不支持**，照旧烧 200 tokens。❌
所以 `llama_server.chat` 现在每次请求都带 `chat_template_kwargs`。被删掉的 Spark 路径当初
就是因为这个原因写死 `enable_thinking=False`——**换引擎时这个坑被一起丢掉了，现在补回来**。

## 第二次真机报错：`exceed_context_size_error`（prompt 16495 > n_ctx 16384）
用户反馈：`导演提示词约 14240 tokens（估算）· 本地导演不可用，使用规则导演：
LlamaServerError: llama-server 返回 400：request (16495 tokens) exceeds the available
context size (16384 tokens)`。**估算值与实测值差 2255 tokens（16%）**，这就是线索。
确认了上一轮的判断：5070 上 55.4 tok/s，确实在 GPU 上跑（6.7GB 权重不可能是 CPU 速度）。

### 两个独立的设计错误
1. **提示词预算 = 整个 `-c`**。`-c` 是**提示词 + 回复**共享的窗口，提示词不可能独占它。
   默认 `-c 16384` 配 `director_prompt_tokens = 16384`，文档里还写着"是自洽的"——不自洽，
   提示词只要超过 `16384 − 4096` 就一定失败。
2. **长度靠字符估算**。中文约 1 字符/token，模板自带的英文样板接近 5 字符/token，
   所以 `/1.8` 在两个方向上都会错；而**低估这一侧是致命的**，因为判据通过、服务器拒收。
   真机这次是低估 16%。

### 修法：能测就别猜，并且只拿该拿的部分
- `LlamaServer` 新增 `context_size()`（读 `/props` 的 `n_ctx`）与 `count_prompt_tokens()`
  —— 后者用 `/apply-template` 渲染真实模板（**同样带 `chat_template_kwargs` 关闭思考**，
  否则数的是请求根本不会发出的那份提示词）再交给 `/tokenize` 数。两个端点都是可选的，
  没有就 `tokenizer_available = False` 退回估算。
- `_prompt_budget()`：`min(director_prompt_tokens, n_ctx − max_new_tokens − 64)`，
  并把算式写进日志，用户能看出预算为什么被压低。`director_prompt_tokens` 从此只是**上界**。
- `_treat_with_llamacpp` **顺序改了**：先起服务 → 算预算 → 拟合提示词 → 生成。
  原来先拟合再起服务，而只有服务器能测量、也只有它知道 `-c` 还剩多少。
- 诊断行从"约 N tokens（估算）"变成"N tokens（服务端实测）· 提示词上限 M（算式…）"。

### 验证（用真实 plan.json 复现）
`my-mv/.beatforge/plan.json` 里有真数据：68 句歌词、341 个素材、253 个镜头、
`director_treatment: null`（证实这个项目从未跑成过导演）。用它重建 brief：
最宽一档的**字符估算 = 14192 tokens**，与用户报的 14240 几乎一致 → 场景复现成功。
修复后：**服务端实测 10563 · 预算 12224**，54.0s 返回完整 10 段方案（色彩弧"晨光 / 暖褐街巷 /
冷蓝返程"、母题与真实素材对得上）。没有 `exceed_context_size_error`。

### 顺带发现（不必深究，但别被误导）
- **`torch.cuda.mem_get_info()` 看不到另一个进程的显存占用**：llama-server 正跑着 6.7GB 权重时它
  仍报"占用 1.89GiB"，且 `-c` 从 8192 扫到 24576 都报同一个数。判断 GPU 是否真在用要看
  **tok/s**（≥20 就是 GPU），不要看这个读数。
- `llama-server` 的日志里**没有** `load_tensors: CUDA0 model buffer size = ...` 这类行，
  所以拿不到权重/KV 的实际显存拆分。`-c 24576` 能正常启动（实测四次都就绪）。
