## 多图合成：堆叠很乱、并排割裂（用户反馈）
用户反馈：「当同一个镜头用两张图片的时候，有一张图片在背后虚化。两张图片重叠在一起的时候，
画面看上去很乱。而且两张图片并排的时候，看起来很割裂」。

### 根因：单图的"留边 + 虚化副本"被用进了合成
`_adapt_image` 是为**一张填不满画面的图片**设计的：按 `image_foreground_scale`（默认 .92）
缩放居中，周围用**同一张图的虚化副本**（`gblur` + 压暗去饱和）补满。
四个多图效果（`split_screen`/`photo_stack`/`double_exposure`/`beat_montage`）**每张图都套了这一层**，
于是错两次：
1. **一帧里有两个互相竞争的虚化底**——每张图各自带一片；
2. **同一张图以两个尺度出现两遍**。

具体表现（渲染出来看过）：
- **堆叠**：底图 = 清晰的自己（92%）叠在自己的虚化副本上，再往上压卡片 → **三个尺度同框**，最乱；
- **并排**：一格走留边处理、另一格全出血 → 两边取景和曝光看着就不一样，读起来像两张恰好挨着的图，
  而不是一张图被切成两半。这就是"割裂"；
- **双重曝光**：两层虚化底一起 screen 混合 → 糊成一片。

### 修复
新增 `_fill_frame()`：`scale=...:force_original_aspect_ratio=increase` + `crop`，**全出血不留边**。
四个合成效果全部改用它；**单图效果仍保留留边处理**（那是它存在的理由——竖图放进横画布时裁掉太可惜）。
堆叠的底图另外压暗去饱和（`eq=brightness=-.085:saturation=.74`），让卡片读得出来。

### 确认过但不是问题的
调色（`_shot_match_filter` / `grade_filter` / `_section_color_filter` / vignette / grain）
是在**合成之后**统一套的（`_image_filter_graph` 返回的标签才进 finishing），
所以两格共享同一个 grade——"割裂"不是调色各调各的造成的。

### 测试（`tests/test_renderer.py` +8 条）
- `test_a_composite_never_letterboxes_a_panel`（4 个效果参数化）：合成图里**不得出现 `gblur`**，
  且必须有 `increase`；
- `test_every_panel_of_a_split_covers_its_slot`（3 个效果）：不得有 `decrease`，
  且恰好 2 个 `increase`；
- `test_a_single_image_still_gets_its_blurred_backdrop`：**单图仍要有 `gblur` 和 `decrease`**——
  这条是防止修复越界，把留边处理从它该在的地方也拿掉。

### 探针
`.probe/composite_probe.py`：用 16:9 和 3:4 两张源图渲染四个合成效果并出接触表——
两种形状才能逼出留边路径。注意要用 `_render_shot()` 而不是 `render()`（单镜头走 `render()`
会在 concat 步骤失败）。

### 关键发现：PIL 的 getname() 会让字体"装了却选不中"
`PIL.ImageFont.getname()` 返回字体**默认语言**的族名。中文商业字体的默认族名常常是中文，
PIL 解码失败 → `"?????"` → 发现阶段读不到 → 永远匹配不上预设。
**但字体本身完全能用**：实测 `Fontname: ZCOOL XiaoWei` 墨量 4019（正常），
`Fontname: 站酷小薇体` 墨量 5425（= Smiley Sans 的回退值，即系统兜底）。

修法：`fonts._font_families()` 直接读 name 表，收集 **name ID 1 和 16、所有平台与语言**的记录。
platform 0/3 用 utf-16-be，platform 1 依次试 utf-8 / gb18030 / latin-1。
副作用是**中文族名也可寻址了**（得意黑、霞鹜文楷、钟齐志莽行书、站酷小薇体）。

  而声明在一个永远选不中的位置等于没加。现在查**解析结果**的集合是否覆盖每个字体文件。
  这条才是真正能挡住"白占仓库体积"的守门测试。
- `test_a_font_with_a_chinese_default_name_is_still_discoverable`：用 ZCOOL XiaoWei 当回归样本。
- 三处枚举族名的旧测试改用 `fonts._font_families()`——**它们原本走的正是被修的那条坏路径**，

## AI 导演换用 Ternary-Bonsai-2-27B（llamacpp 引擎）
用户需求：用 `prism-ml/Ternary-Bonsai-2-27B-gguf` 代替 `XHToken/Spark-X2.5-4B` 当 AI 导演；
并「提示词优化一下，现在可以支持更多的上下文了」。

### 为什么必须换运行时（不是换权重那么简单）
三值检查点**只有 GGUF**，且需要 **PrismML 的 llama.cpp 分支**（三值混合注意力内核）。
原版 llama.cpp 要么拒绝这种量化类型，要么**加载成功但输出乱码**（缺 Hadamard 激活运行时）。
所以报错信息里直接点名分支和下载地址——装错构建的人不会立刻发现，只会在很久以后拿到一堆废话。

### 架构
- 新增 `beatforge/models/llama_server.py`：托管 `llama-server` 子进程，走 `/v1/chat/completions`，
  用**服务端 JSON schema** 约束输出（自由 JSON 正是 2-bit 模型最容易翻车的地方）。
- `director_engine` ∈ {`llamacpp`（默认）, `transformers`}，两条路径共用同一套
  "拟合提示词 → 生成 → 校验 → **一次**修复重试"流程。
- `director_llama_url` 可指向已运行的 server：省掉一次 7GB 加载，也避免同一份权重在显存里存两份。
- llamacpp 暂不支持多模态（Bonsai 有 mmproj 视觉塔，但要另做）；**显式报错而不是静默忽略联系表**——
  静默丢掉图片会让导演对没看过的素材给出自信的答案。

### 提示词：约束变了，预算跟着变
- 旧上限 2600 的**原因**是 Spark 的注意力是手写 `torch.matmul` + softmax，开销**平方增长**。
- Bonsai 约 75% 层是线性注意力，瓶颈从"平方注意力矩阵"变成 **KV 缓存**（由 `-c` 决定，
  llama.cpp 按整个窗口一次性分配）。默认 `-c 16384` + `director_prompt_tokens = 16384` 自洽。
