## MoviePy 方向作废（上午，未落地）
- 用户曾要求"渲染模块改为 MoviePy 驱动、取消 ffmpeg 命令行"。做了可行性评估后，用户改口放弃，
  仓库回滚到 `6c851bd`，MoviePy 依赖与 `beatforge/render/` 包均已清除，`uv sync` 已还原 pillow 12.3.0。
- 评估结论（以后若再被问到可直接引用）：MoviePy 本身不渲染，它是 ffmpeg 的 Python 包装
  （`imageio-ffmpeg` 自带二进制），所以"取消 ffmpeg 命令行"只能做到"不再自己拼命令行"。
  真正的代价是能力净减：只有 `CrossFadeIn` 一个转场（现库有 58 个）、字幕退回 PIL 文本（丢掉 libass 的
  逐字 `\k` 高亮与字体回退）、`perspective` 逐帧运镜要改成逐帧 PIL 仿射，且每帧多一次 numpy 往返。

## 收尾复查：又挖出两个真 bug（同日晚些）
三项扩充做完后回头核对"新东西是否真的被用上"，挖出两个各自独立的真 bug：

### 1. `whip_pan` 甩不起来（位移只有 8px）
可平移量程正比于 zoom：pan 位移 = `(W - W/zoom) × 比例`。原配置 zoom_to=0.045，
整段位移只有 8px @640，无论名义上多快都只是慢漂移。改成 zoom_to=0.42 后位移 46px。
`drag` 的权重核也改成按帧数生成的三角核（`min(i+1, n-i)`），5 帧即 `1 2 3 2 1`。
隔离验证 `tmix` 确实生效：同一段平移，相邻帧差 22.42（无）→ 21.23（3 帧）→ 20.40（5 帧），
拖影把相邻帧桥接起来，这正是运动模糊该有的效果。
（注意：直接看边缘能量会被 `perspective` 的重采样干扰——像素级噪点测试卡一重采样就掉，
测不出 tmix 本身。要用**结构化**测试卡 + 相邻帧差。）

### 2. 运镜轮转被多图合成"饿死"（13/21 种）
`_choose_image_effect` 的合成门控和 `_single_image_effect` 的轮转**共用全局 `index`**。
被合成吃掉的序号，其轮转槽位就永远轮不到：同一首歌的冲击段 9 个镜头里，
非合成的只有序号 18/21/23（余数 3、1、3），槽位 0（`punch_in`）和 2（`whip_pan`）全部落空。
改成 `create_plan` 维护 `single_image_cursor`（`_choose_image_effect` 返回 `layer_count == 0`
时递增），轮转按 cursor 推进。同一首歌从 13 种提升到**用满 21 种**。
- 教训：单个样本歌曲测不出这类饿死——覆盖率取决于该曲的段落和能量分布。第一次扫描时
  我的合成歌曲副歌能量刚好卡在 `.65` 边界，导致 4 个冲击运镜全没选中，误判成"分支够不到"。
  已加 `test_every_camera_move_is_reachable_from_some_song` 跨 28 首歌曲扫描。
- 顺带删掉 `tests/test_planner.py` 里**重复定义第二遍**的 `_varied_song`。

### 新增守门测试
- `test_the_whip_pan_travels_far_enough_to_be_a_whip`：位移 > 5% 画宽 + 图里有 `tmix`。
- `test_a_drag_is_only_asked_for_by_moves_that_need_one`：`tmix` 只允许出现在 `whip_pan` 上
  （它要额外帧缓冲且会软化画面，挂在慢推镜上只会让画面显脏）。
- `test_every_camera_move_is_reachable_from_some_song`：跨歌曲扫全部 21 种运镜。
- 全量 **228 passed**。

### 3. 转场族同样被"相位饿死"（4 个族永远轮不到）
同一类问题的第二种成因。转场的轮转原本按**镜头序号** `index % N`，而转场分支很窄
（`open` 只在 dreamy 歌曲的段落切换处出现，一首歌只有两三次），几次触发可能全落在同一余数上。
实测 `close`/`open`/`radial` 三个族在整个扫描里出现 0 次。

修法：`_assign_transitions` 维护 `visible`（已分配的**可见**转场数），轮转按它推进；
密度门控仍用镜头序号 `index`——两者回答不同问题，所以 `_transition_family` 现在同时接收
`index` 和 `visible`，且改成关键字参数（两个 int 挨着太容易传错）。
- 效果：`light_leak` 从 0 变成可达；`visible` 让同一分支的连续触发取连续槽位，
  分支触发次数 ≥ 轮转长度时就能覆盖全组。
- **可达性还取决于歌曲本身**：第一版扫描用固定段落布局，副歌边界能量恒 >.78，
  被 `flash` 分支抢占，所以 `radial` 永远轮不到——那不是代码 bug，是样本太窄。
  用随机化歌曲（不同段落布局 + 能量曲线）重扫后 **24 族全部可达**。
- 补 `test_every_transition_family_is_reachable_from_some_song`：用**穷举找出**的 8 组
  (段落布局, 能量形状, 情绪) 组合覆盖全部 24 族（单首固定歌曲只覆盖约一半）。
  这 8 组是脚本扫出来的最小覆盖面，不是手猜的。

全量 **230 passed**（35s；一次 70s 的读数是系统负载，重跑即恢复）。

## 视觉检索：把素材压到编码器预算内（傍晚）
用户需求：「WeMM-Embedding + Qwen3-VL Reranker 的时候，将素材压缩至合理范围内，
以减少对显存的占用和提高效率」。

### 问题
Qwen-VL 系 processor 在视觉塔之前会自己把图缩到 `max_pixels = 1280*28*28` ≈ 1.0MP。
所以把 24MP 原图交给它**换不来任何模型能看到的细节**，只换来全分辨率解码 + 全分辨率缩放 +
两者同时在内存里。而原实现有两处直接喂原始分辨率：
1. **图片素材以原始文件路径喂模型**（`str(asset.file)` / `{"image": str(asset.file)}`），
   编码和重排各一次；
2. **重排阶段对每个候选都重新解码原图**——同一张素材在候选表里通常出现好几次，
   浪费是乘以候选数的。
另外视频抽帧固定 `scale=768:-2`，对竖屏失效（768x2048 仍是 1.5MP）。

### 改动
- `AIConfig.vision_input_pixels`（默认 `1280*28*28`）。
- `_fit_within(w, h, max_pixels)`：按**像素预算**而不是长边缩放（长边规则的失效模式正是竖屏），
  只缩不放，并取偶（yuv420p 与 patch 网格都要偶数）。
- `_model_image(asset)`：图片素材的预算内缓存副本（`cache/model-input/`），
  编码与重排共用；本来就在预算内的素材**原样透传**，连缓存目录都不建。
  存副本时用 Pillow 的 `source.draft("RGB", target)` 走 JPEG 的 1/2、1/4、1/8 免解码降采样，
  大文件连全分辨率解码都省掉。
- `_video_frame_samples` 改为按素材实际尺寸算出预算内尺寸，并把该尺寸写进缓存 key
  （否则改预算会静默复用旧尺寸的帧）。
- `_video_frame_at(asset, count, target_time)`：重排只回读它真正需要的那一帧。
- `similarities` 在聚合循环里用完关键帧后立刻把 `spans[position]` 的 frames 置 None，
  不再把整套采样帧持有到整轮结束（重排原本还要再拿一次）。
- SigLIP2 回退路径也走 `_load_bounded_image`。
- `VisionIndex.input_pixels` 设成**类属性**，这样用 `__new__` 绕过构造器的测试仍有合理默认值。

### 实测（`scripts/vision_input_probe.py`，两条路径各起一个子进程，峰值读数才各归各的）
8 张 6000x4000 照片：耗时 1.29s → 0.80s；峰值内存 224 MiB → 61 MiB；
**送进模型的像素 192.00 MP → 8.02 MP（少 23.9x）**。
最后一项才是显存那本账上的数字：视觉编码器的 patch 数量和激活显存直接按像素数走，
而且重排阶段要乘以候选数。
- 写这个探针时踩到：Windows 上 `ctypes` 调 `GetProcessMemoryInfo` **必须显式声明
  `argtypes`/`restype`**，否则不报错、直接返回 0（第一版读数就是 0 MiB）。
  另外 `resource` 模块是 Unix-only，得用 `ctypes` 走 Windows 分支。

全量 **233 passed**。

## 字幕融入画面（参考官方歌词 MV）
用户需求：「有没有可能，将字幕融入到画面中。并且做出一些效果，比如这个MV一样」，
并给了参考片 `利比《跳楼机》(官方歌词MV)`。用户明确说**不需要英文译文**。

### 先看参考片做了什么（`ffmpeg` 抽帧 + tile 网格 + 连续帧序列）
参考片不用底部字幕条。抽 2fps 连续帧后确认的手法：
1. **按演唱位置切句**：一句歌词拆成分片，摆在画面不同位置；
2. **每片在自己被唱到的时刻淡入**（连续帧里"那天的天气"先出现、"难得 放晴"后出现，两者同时停留，
   下一句起来时上一片还在）——这是它读起来"在画面里"的核心；
3. **主动避开主体**：字落在人形之外的空处，有时上下夹持（主体在中间）、有时对角、有时同基线拉开间距；
4. **衬线细体、纯白、无描边**；
5. 器乐段不出字。

关键判断：**不是按字数平分**。最初按字数中点切，得到"黎明照 / 亮天空"——把"照亮"劈开了。

### 实现
- `lyrics.py` 新增 `Placement`（text/x/y/align/tokens/start）+ `plan_placements()`：
  断点取**逐字时间轴里最长的静音**（`_MIN_BREAK_SECONDS = 0.22`）→ 退到标点 → 都没有则**整句不拆**。
  落点用 `shot.focus_point` 避让：主体偏上整组下压、偏下上抬，只有居中才用完整版式。
  三种版式：`sandwich`（上下夹持）/ `diagonal`（对角）/ `gap`（同基线拉开）。
- `_fragment_entrance()`：每片 `\alpha&HFF&` + `\t(delay, delay+260, \alpha&H00&)`，
  delay 由 `placement.start - line.start` 算出。**必须追加在特效标签之后**——libass 按顺序应用
  `\t` 链，后写的对同一属性胜出。同时把特效自带的 `\fad(in,out)` 的入场半边改成 `\fad(0,out)`，
  否则两个 alpha 动画会互相打架。
- 自由版式下 `karaoke` 不再逐字扫光（`_karaoke_fragment` 直接返回纯文本）：分片已经承载了时间信息，
  再扫一遍是把同一件事说两遍。`band` 版式保留扫光。
- `renderer.py` 新增 `_subtitle_placements()` + `_lyric_focus_points()`（按时间一次走完，不重复搜镜头）。
- 配置：`subtitle_layout`（默认 `free`）、`subtitle_outline`（默认 1.1）、`subtitle_fill`（默认 `solid`）。

### 镂空填充（`subtitle_fill = "knockout"`）
"融入画面"的字面做法：没有字幕层，只有画面里一个字形空洞，字中透出同一帧提亮虚化的样子。
- 遮罩 = 同一份歌词脚本渲染成白字黑底，`format=gray` 后用 `alphamerge` 取亮度当 alpha，
  所以脚本里任何动画（淡入/缩放/分片延迟）都会让空洞同步跟随。
- **踩到的坑**：只提亮填充是不够的。自由版式故意把字放在画面空处，那里平滑而暗，
  实测文字对比度是 **−6.2**（比周围还暗）。改成**同时把画面整体压暗**（`_KNOCKOUT_LIFT=0.16`,
  `_KNOCKOUT_DIM=-0.10`）后对比度变成 **+47 / +10**，成为滤镜图的固有属性而不是碰巧。
- `_knockout_graph(subtitle, seconds, cfg)` 的时长改成**参数传入**，不在里面调 ffprobe——测试里
  没有真实视频文件，而且这样职责更清楚。

### 新增探针与测试
- `scripts/subtitle_layout_probe.py`：**不依赖 LRC**（自由排版要的"歌手在哪换气"LRC 带不了），
  直接构造带逐字时间轴的歌词走真实 `render()`，把每个镜头三帧铺成接触表。
  `--layout free|band`、`--fill solid|knockout`。
- 测试：断句落在停顿处（不是中点）、无停顿不拆、标点拆分、避让主体、分片延迟出场、
  band 版式不变、描边可配、镂空图的对比度由构造保证、镂空真的渲染出来且与 solid 不同。

### 顺手修的
- 追加测试块时 heredoc 被执行了两次，`tests/test_lyrics.py` 和 `tests/test_renderer.py`
  各多出一整份重复定义。已删掉，并跑了一遍全仓 `def`/`class` 重复检查确认干净。
- `_fit_font_size` 里的"视觉宽度"计算与新增的 `_visual_units` 重复，已合并到后者。

全量 **242 passed**。

## 剪辑风格：把专家决策结构化为可选配置
用户需求：「我们想创作MV视频内容，但剪辑技术和创意需要提升，请短视频剪辑教练帮我们提升短视频制作水平。
将剪辑专家的技术和创意都结构化为可选配置」。当前会话挂的 Expert 是 `ShortVideoEditingCoach`。

### 设计判断
**剪辑不是"look"**。调色/字体/颗粒属于艺术指导，读的是同一首歌；这一层只管**关于时间的决定**：
镜长、切点网格、转场音量、景别对比、运镜强度。所以新建了 `beatforge/editing.py`，
和 `director.py`（艺术指导）、`planner.py`（编排）分开。

八种风格各自是**一套自洽的习惯**，不是一堆独立旋钮——挑一半"卡点"再挑一半"长镜"，
剪出来就是没有观点的片子。`edit_style = auto` 按情绪选；`manual` 表示"我手工设了值，别接管"。

### 新增能力（不是只加配置入口）
1. **`cut_alignment` 切点网格**：拍 / 小节线 / 乐句 / 歌词行。原本只有 downbeats。
   这是整个文件里最听得出来的一个决定。
   **乐句网格必须按风格自己的镜长窗口自适应取几小节**——固定四小节在 120bpm 下是 8 秒，
   而镜长上限 6 秒的风格永远找不到候选点，会静默退化成按小节切，字段就成了装饰。
2. **`section_speedup` 段落内加速**：越接近本段顶点镜头越短。
3. **`transition_flavour` 转场取向**：含蓄/均衡/冲击，各自一套内部转场池 + 降级替代表。
4. **`shot_size_contrast`**：原本写死 -0.09，现在由风格给出（0.08~0.22）。

### 踩到 / 修掉的三个真问题
1. **`transition_density` 几乎不起作用**：`impact`/`breathe` 两个意图分支在密度门控**之前**就返回了，
   所以密度压不住它们——一个只想要 10% 可见转场的纪实风格实测仍有 47%。把门控提到意图分支之前。
2. **`_quieten` 只在一个分支里调用**，所以含蓄风格的结构性转场仍然会出现闪白/故障。改成所有出口统一过滤。
3. **风格给了 `transition_density`，但被 `create_plan` 的默认值 0.35 盖住**——只有调用方显式传才生效。
   改成"风格接管它表过态的项"（镜长、转场密度、多图比例），其余仍走参数。这是同一个病：
   **配置被接受但没生效**，这一轮已经是第二次（上次是 `_KNOCKOUT_LIFT`）。
4. `montage` 原本用 `phrase`，但它的镜长上限 3.6s 装不下一小节，等于该字段对它无效 → 改回 `downbeat`；
   `dream` 和 `minimal` 原本都落在同一个乐句网格上、中位镜长都是 6.00s → 把 `minimal` 拉到 4.0–9.0s。

### 验证
`scripts/edit_style_probe.py`：把同一首歌喂给全部八种风格，打印镜头数/镜长/可见转场/转场音量/
景别撞车率。实测镜头中位 **0.50s（冲击碎剪）~ 8.00s（极简留白），差 16 倍**；
可见转场 **10%（纪实）~ 70%（冲击）**；含蓄风格冲击转场占比 **0%**。
写探针时踩到：素材景别按索引交替的话，**所有风格都会 100% 换景别**，指标失去意义——
改成**成块分布**（每 7 个素材同景别）才测得出 `shot_size_contrast`（实测同景别相邻 34% → 3%）。
